# 意思決定ログ（協業記録）

このドキュメントは、ユーザーとエージェント（Kiro）の協業の中で行った **重要な変更・意思決定** を時系列で記録したものです。「何を問われ、ユーザーがどう判断し、結果どうなったか」を残し、後から経緯をたどれるようにします。

> 記録方針: ユーザーの判断はできる限りそのままの言葉で残し、言い換えによる歪みを避けています。日付は 2026-10-08〜10-09 のセッション。

---

## 凡例

- **論点**: そのターンで何が問われたか／何が問題だったか
- **ユーザーの判断**: ユーザーが選んだこと（原則、本人の言葉ベース）
- **結果・影響**: その判断で何が起きたか、どこに反映されたか

---

## 1. 進め方のルールの確立（協業スタイル）

- **論点**: ワークフローをどのペースで、どこまでユーザー確認を取りながら進めるか
- **ユーザーの判断**: 一歩ずつ、明示的なゴーサインを待って進める。回答は言い換えずそのまま記録する。コマンド実行は毎回承認を取る。方針・設計の具体化はユーザーが決める。
- **結果・影響**: `aidlc/spaces/default/memory/project.md` の「進め方のルール」として恒久ルール化。以降の全ステージでこの原則に従って進行。

## 2. build-and-test のやり直し（ドリフト対応）

- **論点**: 完了済み `build-and-test` に「ドリフト（advisory）」が検知されていた。やり直すか、助言のまま進むか。
- **ユーザーの判断**: やり直す（単独再実行）。実測コマンドは都度確認なしの一括ゴーサインで進める。
- **結果・影響**: `--stage build-and-test --single` で再実行。backend/frontend ともすべてグリーンを再確認し、2026-10-07 の記録と同一結果であることを `test-results.md` / `build-and-test-summary.md` に追記。

## 3. observability-setup の方針（最小構成）

- **論点**: 観測性セットアップの7成果物を、ローカル・お試し用途に対しどこまで実体を持たせるか。
- **ユーザーの判断**: 最小構成に絞る。
- **結果・影響**: 実体ある観測性はサービス層トレース（DEBUG）＋業務例外（WARN）＋ログ検索指針に限定。SLO/アラート/ダッシュボード/分散トレーシング/異常検知は「ローカル・お試し用途のためスコープ外」を理由付きで明記。承認ゲートを正式手順（サマリ確認記録→承認）で通過。

## 4. 承認ゲートのガード対応（根本原因の特定）

- **論点**: observability-setup の完了承認が strict ガードで繰り返し拒否された（SUMMARY_ARTIFACT_UNAUTHORIZED / SUMMARY_CONTENT_STALE）。
- **ユーザーの判断**: ファイル手編集を繰り返さず、根本原因を特定して正式手順で進める方を選択。
- **結果・影響**: エンジンが「サマリ質問の記録 → 新しい人間ターンでの確認 → authorization id でスタンプされた成果物の再保存 → 完了承認」という監査イベント連鎖で承認を追跡していることを特定。以降この正式手順で承認ゲートを通過するようになった（performance-validation でも踏襲）。

## 5. performance-validation の方針（軽量・実測ベース）

- **論点**: 性能検証を実測で行うか、ドキュメントのみにするか。
- **ユーザーの判断**: 軽量・実測ベース。実測フローは一括ゴーサイン、計測後はテストデータを削除しDBをクリーンに戻す。
- **結果・影響**: 300件投入し GET/POST/DELETE を各5回計測。一覧17ms / 作成2.4ms / 削除8ms で努力目標の目安をすべて達成（`performance-validation/test-results.md`）。

## 6. 本番ローカル実行設定の起動バグ発見と修正

- **論点**: 性能実測でバックエンドを起動した際、H2 2.1.214 で `AUTO_SERVER=TRUE;DB_CLOSE_ON_EXIT=FALSE` の同時指定が "Feature not supported" となり起動失敗。build-and-test はテスト専用設定（インメモリ）で走っていたため未検出だった。
- **ユーザーの判断**: 設定を修正してから実測を続ける。
- **結果・影響**: `application.properties` の接続URLから `DB_CLOSE_ON_EXIT=FALSE` を削除。正常起動を確認し実測を完了。コード側の潜在バグを運用フェーズの実測で検出・修正した事例。

## 7. ワークフロー完了

- **論点**: 残ステージの有無確認。
- **結果・影響**: `greenfield-webapp` スコープの実行対象ステージ（計16、ci-pipeline はスキップ）がすべて完了。`WORKFLOW_COMPLETED`。

## 8. ドキュメント整備

- **論点**: プロジェクトの実行方法・AI-DLC の使い方・新規参加者向けの案内をどう残すか。
- **ユーザーの判断**: 実行手順書を作成。AI-DLC でアプリを作る際の README と、初めて見る人向けのスタートアップ資料ガイドを作成。各資料の冒頭にアジェンダを追加。ディレクトリ早見表は読む順ガイドの先頭に配置。
- **結果・影響**: `RUNBOOK.md`（実行手順）、`docs/AIDLC-GUIDE.md`（AI-DLC ガイド）、`ONBOARDING.md`（読む順案内）を作成。全説明資料（README 含む）の冒頭に「この資料の内容（アジェンダ）」を追加。ONBOARDING のディレクトリ早見表を読む順ガイド先頭へ移動。

## 9. サンプルデータの投入と data.sql 同梱

- **論点**: サンプルデータをどう用意し、どう共有可能にするか。H2 ファイルDBは `.gitignore` で除外されるため Git 共有では渡らない。
- **ユーザーの判断**: まず API 経由でサンプルを投入（データは残す）。その後、Git で共有しても誰でも同じ初期データで起動できるよう `data.sql` を同梱。同梱SQLでサンプルが作成される旨を手順書に追記。
- **結果・影響**: `backend/src/main/resources/data.sql`（13件、空のときだけ投入する冪等SQL）を作成。`application.properties` に `defer-datasource-initialization=true` / `spring.sql.init.mode=always` を追加。空DB起動で13件自動投入、再起動で重複なしを実測確認。`RUNBOOK.md` に §4.5 を追記。

## 10. GitHub への公開（Private）

- **論点**: プロジェクト成果物を GitHub に公開するか、公開範囲・AI-DLC 成果物の扱いをどうするか。
- **ユーザーの判断**: Private で公開。AI-DLC 成果物（`aidlc/`）も含めて公開。
- **補足（確認した事実）**: 同梱の AGENTS.md「Git Integration」より、AI-DLC は `aidlc/` を版管理する前提であり、成果物のコミットを非推奨とする記載はない。機微情報を含みうるものは `.gitignore` で除外済み。
- **結果・影響**: 秘密情報スキャン（本物の鍵・トークンなし）を確認後、git 初期化・初回コミット（`e9daac4`）・push。リポジトリ https://github.com/masayuki-tahira0509/aidlc_sample （Private）。監査ログ更新を追加コミット（`052a586`）して push。`node_modules` / `backend/target` / `backend/data`（DBファイル）は除外。
