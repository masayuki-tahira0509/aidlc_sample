# Security Requirements — 社内お知らせ掲示板

## Sources

- [requirements] C1: 認証・ログインなし（社内ネットワーク前提）。C2: 権限管理・ロールなし。C3: 外部連携なし。NFR2: ローカル実行。
- [Q3-prior] 投稿者名は認証がないため自己申告（A2）。
- [construction-phase] Construction フェーズのセキュリティガードレール: 認証/認可をバイパスするコードを明示、入力は境界で検証・サニタイズ、秘密情報のハードコード禁止。

## セキュリティ方針（本プロジェクトの前提）

本アプリは認証・認可を持たない（C1/C2）。これは社内ネットワーク前提かつお試し・学習用途という明示的なスコープ判断であり、「認証を実装しない」ことは要件であって欠陥ではない。したがってセキュリティ要件は、認証なし前提で現実的に意味のある項目（入力検証・出力エスケープ・秘密情報の非混入・最小限のログ衛生）に絞る。 [C1][C2]

## 要件一覧

### NFR-SEC（認証・認可）

- **NFR-SEC.1** 認証機能は実装しない（C1）。投稿者名は自己申告の手入力であり、本人性は保証しない（A2）。この前提をREADME等に明記し、将来の認証追加余地を OQ1 として残す。 [C1][A2]
- **NFR-SEC.2** ロール・権限分離は行わない（C2）。すべての操作（CRUD）は無差別に許可される。認証/認可をバイパスする「隠れた」経路を作らない（そもそも認可層が無いことを設計上明示する）。 [C2]

### NFR-SEC（入力検証・インジェクション対策）

- **NFR-SEC.3** すべての入力（タイトル・本文・投稿者名・カテゴリ）はバックエンドの境界で検証する。必須項目（タイトル・本文・カテゴリ）の空チェックと、文字数上限（暫定: タイトル100字・本文2000字、確定はOQ5）を適用する。クライアント側検証はUX目的であり、サーバ側検証を正とする。 [FR2.6][construction-phase]
- **NFR-SEC.4** データアクセスは Spring Data JPA のパラメータバインディング（プリペアド文）を用い、文字列連結によるSQL組み立てを行わない。SQLインジェクションを構造的に排除する。 [construction-phase]
- **NFR-SEC.5** カテゴリは許可リスト（暫定: 一般/重要/業務連絡）で受け付け、リスト外の値を拒否する。 [FR5.2][A3]

### NFR-SEC（出力・XSS 対策）

- **NFR-SEC.6** 本文等のユーザー入力を画面表示する際は、React のデフォルトエスケープに依拠し、`dangerouslySetInnerHTML` を使用しない。本文の改行保持（FR2.5）はエスケープ済みテキストに対する CSS/改行変換で行い、生HTML描画はしない。XSS を構造的に防ぐ。 [FR2.5][construction-phase]

### NFR-SEC（秘密情報・設定衛生）

- **NFR-SEC.7** 認証情報・APIキー・シークレットをコードにハードコードしない。本アプリは外部シークレットを持たないが、H2 の接続設定等は設定ファイルで管理し、不要な認証情報を含めない。 [construction-phase]
- **NFR-SEC.8** ログに個人情報・入力本文の全文を無制限に出力しない。エラーログは原因究明に必要な範囲に留める（観測性要件と整合）。 [construction-phase]

### NFR-SEC（通信・実行環境）

- **NFR-SEC.9** ローカル実行前提のため TLS は必須としない（NFR2）。将来、社内ネットワーク外への公開を行う場合は TLS 化と認証追加（OQ1）を再評価する。 [NFR2][OQ1]
- **NFR-SEC.10** CORS はローカル開発構成（frontend と backend の別ポート）で必要最小限のオリジンのみ許可する。ワイルドカード全許可は避ける。 [Q2][construction-phase]

## 脅威の簡易評価（STRIDE 観点、ローカル・認証なし前提）

| 脅威 | 本アプリでの扱い |
|------|----------------|
| Spoofing（なりすまし） | 認証なしのため投稿者名の本人性は非保証（既知の受容リスク、A2/C1） |
| Tampering（改ざん） | 入力検証（NFR-SEC.3）とパラメータバインディング（NFR-SEC.4）で境界を保護 |
| Repudiation（否認） | 監査ログは本スコープ外。投稿日時の記録のみ（FR2.3） |
| Information Disclosure（情報漏えい） | ローカル・単一利用者前提。ログ衛生（NFR-SEC.8）で最小化 |
| Denial of Service | 単一利用者ローカルのため対象外。全件表示の件数増は NFR9/スケーラビリティで扱う |
| Elevation of Privilege | 権限分離が無いため該当なし（全操作が等権限、C2） |

## Assumptions & Open Questions

- [assumption] 認証・認可の不在は明示的なスコープ判断（C1/C2）。受容リスクとして記録済み（A2）。
- [open-question] OQ1: 将来の認証追加時に、認証方式・ロール・投稿者名の紐付けを再確定する。
- [open-question] OQ5: 入力バリデーションの詳細（最大文字数・エラーメッセージ）は Functional Design / 実装時に確定。
