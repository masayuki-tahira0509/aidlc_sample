## Intent Analysis（意図分析）

社内の従業員が、お知らせ・アナウンスを一元的に閲覧できる場を持たないという課題を解決する。目的は「必要な情報を探し回る手間をなくし、お知らせを1か所で確認・管理できるようにすること」。本プロジェクトは技術探索・学習も兼ねた個人開発で、React（フロントエンド）と Java / Spring Boot（バックエンド）を組み合わせた実践的なWebアプリ構築を狙う。 [intent-statement] [scope-document]

まず価値のある最小構成（お知らせのフルCRUD）を動く状態で届けることを優先する。 [scope-document]

## Functional Requirements（機能要件）

### FR1. お知らせ一覧表示

- FR1.1 登録済みのお知らせを一覧画面に表示する。 [IS-1]
- FR1.2 一覧は投稿日時の新しい順（降順）で表示する。 [Q4]
- FR1.3 一覧はページングを設けず全件表示とする（お試し用途のため）。 [assumption]
- FR1.4 各お知らせについて、少なくともタイトル・投稿者名・投稿日時・カテゴリを一覧上で判別できる。 [Q1]

### FR2. お知らせ新規登録（Create）

- FR2.1 新規お知らせを登録できる。 [IS-2]
- FR2.2 登録フォームはタイトル、本文、投稿者名、カテゴリの入力を受け付ける。 [Q1] [Q2-F]
- FR2.3 投稿日時は登録時にシステムが自動付与する。 [Q1]
- FR2.4 投稿者名が未入力の場合は、既定値（例: "名無し"）を自動補完する。 [Q2-F]
- FR2.5 本文は複数行テキストとして入力・保存する（改行を保持。Markdown やリッチテキストの装飾は対象外）。 [Q3]
- FR2.6 タイトルと本文は必須入力とする（空では登録不可）。カテゴリは必須とし、投稿者名は任意（未入力時は FR2.4 の既定値）。各項目の最大文字数などの詳細な検証ルールは Functional Design / 実装時に確定する。 [R-01] [open-question]

### FR3. お知らせ編集（Update）

- FR3.1 既存のお知らせを選択して内容を編集できる。 [IS-3]
- FR3.2 編集対象はタイトル、本文、投稿者名、カテゴリとする。 [Q1]
- FR3.3 投稿日時は編集時に変更しない（登録時の値を維持する）。 [assumption]

### FR4. お知らせ削除（Delete）

- FR4.1 既存のお知らせを削除できる。 [IS-4]
- FR4.2 削除操作の前に確認ダイアログを表示し、ユーザーの確認を得てから削除する。 [Q5]

### FR5. お知らせのデータ項目

- FR5.1 お知らせは次の項目を持つ: タイトル、本文、投稿者名、投稿日時、カテゴリ（お知らせ種別）。 [Q1]
- FR5.2 カテゴリは「お知らせ種別」を表す区分であり、登録・編集時に指定する。具体的な区分値は Functional Design / 実装時に確定する。 [Q1] [open-question]

## Non-Functional Requirements（非機能要件）

- NFR1 データ永続化: 登録・編集・削除したお知らせは、アプリケーション再起動後もデータが保持される（ファイルベースのDBで永続化。例: SQLite / H2 ファイルモード）。 [Q6-F]
- NFR2 実行環境: ローカル環境で動作すること。本番相当のデプロイパイプラインは本スコープ外。 [scope-document]
- NFR3 技術スタック: フロントエンドは React、バックエンドは Java（Spring Boot を推奨）。 [scope-document]
- NFR4 テスト容易性: バックエンドの主要CRUDロジックにはハッピーパスの単体テストを用意できる構造とする（test-after 方針）。 [team-practices]
- NFR5 コード品質: React 側は ESLint + Prettier を適用する。 [team-practices]
- NFR6 ユーザビリティ: 一覧・登録・編集・削除の操作が、画面上の明示的なUI要素（ボタン・フォーム）から行えること。 [intent-statement]
- NFR7 保守性・変更容易性: 将来の機能追加・修正にかかるコストを最小化することを設計目標とする。合否基準として、(a) フロントエンド／バックエンドを分離し、バックエンドはプレゼンテーション層・ビジネスロジック層・データアクセス層を明確に分けること、(b) お知らせの永続化手段（DB実装）を上位ロジックから差し替え可能にすること（例: リポジトリ/インターフェースによる抽象化）、(c) team-practices の命名規約・ESLint/Prettier を適用すること。 [ユーザー要望: スケーラビリティ=修正コスト最小化] [team-practices]
- NFR8 拡張容易性: 現在スコープ外の機能（認証、検索・フィルタ、カテゴリ区分の追加、通知など）を後から追加しやすい構造とする。合否基準として、お知らせのデータモデルとAPIが項目追加・機能追加に対して局所的な変更で対応できること。学習目的として拡張性の作り込みを行う方針（B-2）だが、単一エンティティCRUDの範囲で妥当なレベルに留め、過剰な抽象化は避ける。 [ユーザー要望] [scope-document]
- NFR9 データ量耐性: お知らせ件数の増加に対して一覧表示が破綻しないこと。MVP では全件表示（FR1.3）とするが、件数増加時に備えページング／遅延読み込みを後付けできる構造とする（実装は将来拡張、OQ4）。 [ユーザー要望: A-3] [R-04]

## Constraints（制約）

- C1 認証・ログイン機能を持たない（社内ネットワーク前提・お試し用途）。 [OS-1] [team-practices]
- C2 権限管理・ロールを持たない（認証がないため）。 [OS-4]
- C3 外部システム連携を行わない（スタンドアロンで完結）。 [OS-2]
- C4 単一エンティティ（お知らせ）のみを対象とする。 [scope-document]

## Assumptions（前提）

- A1 一覧の表示件数が増えてもページングは当面不要（お試し用途・全件表示）。 [assumption]
- A2 投稿者名は認証がないため自己申告（手入力）であり、本人性は保証しない。 [Q2-F]
- A3 カテゴリの区分値は設計・実装時に確定する（例: 一般 / 重要 / 業務連絡 など）。 [Q1]
- A4 編集時に投稿日時は更新しない。更新日時の管理が必要になった場合は将来拡張とする。 [assumption]

## Out of Scope（対象外）

- OOS1 認証・ログイン機能。 [OS-1]
- OOS2 権限管理・ロール。 [OS-4]
- OOS3 外部システム連携。 [OS-2]
- OOS4 検索・フィルタ機能。 [OS-3]
- OOS5 通知機能（メール等）。 [OS-5]

## Open Questions / 将来の拡張候補

- OQ1 認証・ログイン機能: 今回はスコープ外。将来的に追加する可能性があるため拡張候補として記録する。追加する場合は、認証方式・権限（ロール）の有無・ユーザー登録の要否・投稿者名をログインユーザーに紐付けるか、をあらためて確定する必要がある。 [ユーザー判断: 一旦スキップ]
- OQ2 カテゴリの具体的な区分値（FR5.2 / A3）。 [open-question]
- OQ3 更新日時・編集履歴の管理（A4）。将来必要になれば検討。 [open-question]
- OQ4 一覧のページング／遅延読み込み（NFR9）。MVP では全件表示とし、件数増加時に導入を検討する。 [R-04]
- OQ5 入力バリデーションの詳細（各項目の最大文字数、エラーメッセージ、異常系の挙動）。FR2.6 の方針を踏まえ Functional Design / 実装時に確定する。 [R-01] [R-03]
