# AI-DLC でアプリケーションを作る — ガイド

このドキュメントは、本プロジェクト（社内お知らせ掲示板）で使っている **AI-DLC（AI-Driven Development Life Cycle）** の使い方をまとめた入門です。「AI-DLC とは何か」「どう始めるか」「どんな流れで進むか」「成果物はどこに残るか」を、このプロジェクトの実例に沿って説明します。

> 対象読者: このリポジトリで AI-DLC を使って開発を進める人、または AI-DLC の進め方を知りたい人。
> 前提ハーネス: Kiro IDE。チャットで `/aidlc` を実行してワークフローを動かします。

## 1. AI-DLC とは

AI-DLC は、アイデアから実装・運用までを **順序立てたステージ** に分け、各ステージの区切りで **人間の承認ゲート** を挟みながら進める開発手法です。要点は3つ:

1. **段階的** — 要件 → 設計 → 実装 → 検証を小さなステージに分けて進める
2. **承認ゲート** — 各ステージの成果物は、人間が承認するまで次に進まない
3. **記録が残る** — 何を決め、何を作ったかが監査ログと成果物として版管理される

「エージェントが勝手に全部作る」のではなく、「要所で人間が方向を決め、エージェントが実作業を担う」協働モデルです。

---

## 2. 始め方（クイックスタート）

Kiro IDE のチャットで、作りたいものを書いて `/aidlc` を実行するだけです。

```
/aidlc 社内向けのお知らせ掲示板を作りたい。React + Spring Boot で、お知らせのCRUDができる最小構成。
```

- スコープ（どれくらいの工程を回すか）は内容から自動判定されます（本プロジェクトは `greenfield-webapp`）。
- 以降はステージごとに質問・成果物提示・承認が繰り返されます。番号や言葉で答えるだけで進みます。

### よく使う操作

| 操作 | コマンド | 用途 |
|------|----------|------|
| 現状確認 | `/aidlc --status` | 今どのフェーズ/ステージか、進捗、ガード設定を表示 |
| 再開 | `/aidlc`（引数なし） | 中断したワークフローを再開（Resume などの選択肢が出る） |
| 特定ステージへ | `/aidlc --stage <slug>` | 例: `/aidlc --stage build-and-test` でそのステージをやり直し |
| フェーズへジャンプ | `/aidlc --phase construction` | そのフェーズの最初の対象ステージへ |
| セットアップ診断 | `/aidlc --doctor` | フック・設定・ディレクトリの健全性チェック |
| 計画の相談 | `/aidlc compose "<やりたいこと>"` | タスクに合わせた工程プランを提案 |

## 3. ワークフローの流れ（5フェーズ）

AI-DLC は5つのフェーズに分かれ、各フェーズに複数ステージがあります。スコープによって一部ステージは SKIP されます。本プロジェクト（`greenfield-webapp`、17ステージ実行 / 一部スキップ）の実例:

| フェーズ | 役割 | 本プロジェクトで実行したステージ |
|----------|------|-------------------------------|
| **Initialization** | 下準備（ワークスペース検出・状態初期化） | workspace-scaffold / workspace-detection / state-init |
| **Ideation**（着想） | 課題と範囲を定める | intent-capture / feasibility / scope-definition / rough-mockups / approval-handoff |
| **Inception**（起案） | 要件・設計の土台を固める | practices-discovery / requirements-analysis / refined-mockups |
| **Construction**（構築） | 実装・テスト | nfr-requirements / code-generation / build-and-test |
| **Operation**（運用） | 観測性・性能など運用面 | observability-setup / performance-validation |

> SKIP されたステージ（例: market-research, user-stories, domain-design, deployment-pipeline など）は、お試し/ローカル用途のスコープ判断で対象外にしたものです。「やらなくていい」と決めた記録が残ります。

### 1ステージの進み方（内部ループ）

各ステージはおおむね次のループで進みます:

1. エンジンが「次にやるステージ」を提示（`next`）
2. エージェントが成果物を作成（必要に応じて質問）
3. **サマリ確認** — 「この内容で確定してよいか」を人間に確認
4. **承認ゲート** — 人間が Approve すると、エンジンが完了を記録（`report`）
5. 次のステージへ

承認は人間の「新しいターン」が必要です（エージェントが勝手に承認扱いにはできません）。これが「要所で人間が決める」の実装です。

## 4. 成果物とルールはどこに残るか

すべて `aidlc/` 配下に版管理されます。

```
aidlc/
├── active-space                        アクティブな space を指すカーソル
└── spaces/default/
    ├── memory/                         方針・ルール（下記）
    │   ├── org.md                      フレームワーク既定＋組織ルール
    │   ├── team.md                     チームの合意事項（進め方・テスト方針など）
    │   ├── project.md                  このプロジェクト固有のルール・学習
    │   └── phases/<phase>.md           フェーズ別ガードレール
    └── intents/<YYMMDD>-<label>/       1つの開発テーマ（intent）の記録
        ├── aidlc-state.md              現在のフェーズ/ステージ/進捗（状態ファイル）
        ├── ideation/ inception/ construction/ operation/   各フェーズの成果物
        ├── audit/*.md                  監査ログ（決定・行動の時系列）
        └── project-description.json    最初の依頼内容
```

- **方針・ルール**（`memory/`）: `org → team → project → phase` の順で重ねて適用。例として本プロジェクトの `project.md` には「一歩ずつ、ユーザーの明示的ゴーサインを待つ」などの進め方ルールが記録されています。
- **成果物**（各フェーズのフォルダ）: requirements.md、設計、テスト結果、観測性方針、性能実測など、ステージごとの産物。
- **監査ログ**（`audit/`）: 「いつ・どのステージで・何を決めたか」のイベント記録。会話全文ではなく構造化された記録です。
- **アプリのコード**: ワークスペース直下（`backend/`・`frontend/`）に出力されます（`aidlc/` の外）。

---

## 5. ガードポリシー（人間の安全装置）

ステージ進行には「ガード」があり、承認の順序や成果物の整合性を守ります。モードは `strict`（既定）/ `relaxed` / `off`。

- 本プロジェクトは `strict`。承認は「サマリ確認を記録 → 新しい人間ターン → 成果物をスタンプ付きで保存 → 完了承認」という順序で進みます。
- 緩めたい場合は人間が明示的にコマンドで切り替えます（例: `/aidlc --guard-policy relaxed`）。エージェント側から勝手には変えられません。

## 6. このプロジェクトでの実例ハイライト

AI-DLC の協働がどう効いたかの実例:

- **方針はユーザーが決定**: 観測性セットアップ・性能検証では、エージェントが選択肢（最小構成/標準/自分で指定）を提示し、ユーザーが選ぶ形で進めました。
- **実測で潜在バグを発見**: 性能検証で実際にアプリを起動した際、本番ローカル実行設定の H2 起動バグ（`AUTO_SERVER=TRUE;DB_CLOSE_ON_EXIT=FALSE` 同時指定が H2 2.x で不可）を検出し、承認のうえ修正しました。テストはテスト専用設定で走るため埋もれていた問題でした。
- **決定の記録が残る**: 「性能は厳密 SLO でなく努力目標」などの判断が `project.md` と各ステージの成果物に残っています。
